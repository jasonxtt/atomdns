## 1. 用户已确认的日志需求（2026-10-24）

用户确认：**对于较早的普通成功查询，能查看客户端、域名、返回 IP/CNAME、分流与最终上游，已经够用。**
不要求为这些普通成功查询长期保留完整 TTL、特殊 RR 正文或全部上游尝试过程。

据此，后续设计以“日常记录较长保留、完整诊断较短保留”为方向：

- 日常记录保留完整最终地址/CNAME 列表、生效分流与命中来源、实际最终上游；建议继续保留时间、QTYPE、结果码、耗时、紧凑缓存/失败状态与关联 ID。
- 完整应答 TTL、TXT/SRV/HTTPS 等特殊 RR 正文、分支树、逐路尝试等作为独立有界详情，优先服务近期、异常、慢查询与主动诊断。
- 用户确认针对较早的**普通成功查询**；错误/慢查询的保留策略、具体条数/时长、总预算及默认值仍需设计。此前举例的“10 万条基本记录、最近数千条完整详情”不是已冻结参数。
- 详情缺失/过期须明确标记；不能用空应答或空尝试列表冒充当时的真实结果。
- 保留 IP/CNAME 搜索时应覆盖完整列表，不能只存首个地址。实际供应者与分流来源保存当时事实，不从当前配置或当前 DNS 缓存推断。

此次授权是记录研究和需求，未授权修改程序、删除现有字段、缩减容量或部署。
现行 [审计契约](../contracts/native-audit-control.md) 仍要求完整无损投影；实施分级保留前须明确 API/WebUI 的详情状态与兼容方案，并更新对应契约。

## 2. 域名哈希压缩的来源与适用边界

截图项目是 [s60sc/ESP32_AdBlocker](https://github.com/s60sc/ESP32_AdBlocker)，其 README 描述需要 PSRAM。
“537k 域名、40 位哈希、ESP32-C3 无需 PSRAM”的实现对应
[M-Abozaid/esp32-c3-adblock](https://github.com/M-Abozaid/esp32-c3-adblock)，本次固定研究提交
`238ef7b27097e8597f39e9a5ce07a958488572a2`。

[构建脚本](https://github.com/M-Abozaid/esp32-c3-adblock/blob/238ef7b27097e8597f39e9a5ce07a958488572a2/tools/build_blocklist.py)
将规范化域名计算为 FNV-1a 64 位哈希，保留低 40 位，排序、去重，以每条 5 字节写入文件。
[查询源码](https://github.com/M-Abozaid/esp32-c3-adblock/blob/238ef7b27097e8597f39e9a5ce07a958488572a2/src/main.cpp)
将主表放在 Flash，RAM 留约 20 KiB 采样索引、小缓存和区间缓冲，匹配查询名字及其父域。

低 RAM 来自“缩小索引”与“主表放在 Flash”两个因素。537,000 条 5 字节记录本体为 2,685,000 字节（约 2.56 MiB），并非完整索引只占 50 KB。

40 位哈希是有碰撞的集合表示，不能还原原文；没有原文核对的命中可能误拦集合外名字。
在独立均匀哈希的理想模型下，537k 条记录的内部碰撞对期望约 0.131，至少一对内部碰撞的概率约 12.3%；
单个集合外候选误中表内值的概率约 `4.88e-7`（约每 205 万个候选一次）。父域匹配会检查多个候选，FNV 实际分布不保证符合该理想模型。
两个已屏蔽域名共用哈希本身不会新增误拦，集合外查询共用哈希才会；原列表零碰撞也不能证明查询零误判。

64 位数组本体约 4.10 MiB，仅比 40 位多约 1.54 MiB，但更低碰撞概率仍不等于严格相等。
**研究建议是保留精确匹配：哈希可作索引/预筛并核对原文，或采用字符串池、紧凑 trie、FST。用户未批准以概率匹配改变默认分流。**

## 3. 当前域名索引与独立实验

### 3.1 源码事实

[DomainSuffixMatcher](../../../rust/matcher-core/src/trie.rs) 已用扁平节点 arena，每节点仍有 `Option<V>` 与 `HashMap<String, usize>`，标签单独分配 String。
主要成本是节点、子表、字符串和预留容量。
[ValuedDomainMatcher](../../../rust/matcher-core/src/valued.rs) 已经共享相同结果 payload；下一步可用小整数 ResultId 替代索引中的 Arc，再查共享 marks/tags/sources。

[Mem-1 历史测量](../validation-records/10-08-mem-1/README.md) 的 140,134 条 domain 规则 trie 请求堆约 21.1 MiB（约 150 B/条），full 规则约 1 MiB。
其中包含未触及容量，不能全额折算 RSS；旧规则数量也不代表今天生产规模。

### 3.2 结果与限制

环境：macOS 26.5.1 arm64，Rust 1.96.0，release 优化。直接依赖研究时的 matcher-core 源码，输入来自相邻配置仓库；未采集线上生产。
以下为 ASCII 后缀规则子集的**存活请求堆 MiB**：含索引已申请容量，不含预先存在的输入域名和查询语料，也不含 malloc 元数据、碎片、代码、栈或系统页缓存。

| 表示 | 文本 88,094 条 | CN SRS 117,508 条 | 非 CN SRS 25,712 条 | 匹配性质 |
| --- | ---: | ---: | ---: | --- |
| 当前后缀 trie | 12.440 | 13.054 | 3.194 | 精确 |
| 当前 valued matcher，单个共享结果 | 12.440 | 13.054 | 3.194 | 精确 |
| 字符串池＋u32 偏移排序表 | 1.294 | 1.744 | 0.432 | 精确 |
| FST 集合 | 0.625 | 1.250 | 0.312 | 精确 |
| FST Map，单个 ResultId | 0.625 | 1.250 | 0.312 | 精确键 |
| FST Map，每键不同 ResultId | 1.250 | 1.250 | 0.312 | 精确键 |
| 排序 40 位哈希 | 0.420 | 0.560 | 0.123 | 概率匹配 |
| 排序 64 位哈希 | 0.672 | 0.897 | 0.196 | 概率匹配 |

88k 子集字符串池比原 trie 少申请约 89.6%，FST 集合约少 95.0%。这是索引比例，不能套算为整个进程的下降比例。
FST 利用公共片段压缩精确键，见 [库文档](https://docs.rs/fst/0.4.7/fst/)；尚未确定最终采用哪个实现或新增产品依赖。
Map 的值只是 ResultId，不含对应业务 payload；不同 ID 实验使用按键序递增的人工 ID，不是任意取值的空间上界。
字符串池若另加每键 u32 结果数组，还需约 4 B/条及真正的结果池。

每份语料选 5,000 个规则，验证精确名字、子域、无关后缀、大小写和尾点，每种表示各重复 5 次，约 300 万次布尔比较，错误计数均为 0。
仅验证所选成员判断，未验证完整 mapper 的继承、来源合并、AdGuard、所有特殊名字和在线更新。
哈希样例零错误也不能证明零误判。查询纳秒值只是微测量，valued 路径还返回元数据，不可推算 DNS QPS/p99。

88k 子集构建增量峰值：当前 valued 约 37.50 MiB，字符串池约 1.29 MiB，FST 带 ResultId 约 7.18–7.80 MiB。
起点是已加载域名向量，未计 SRS 解压、文件读取或仍服务的旧代，不能当作热应用峰值验收。

### 3.3 候选设计

先压缩 domain/full 的只读键索引，保留 regexp、keyword 语义；候选为“紧凑键索引 → ResultId → 共享结果”。
字符串池＋排序表可作改动较小的基线，再比较连续子边表的紧凑 trie 与 FST Map。
原始规则文件继续用于显示、搜索、编辑、下载和回滚；日志中的查询名也保留可恢复的精确原文。

必须保持 full 边界、最长后缀、root/空标签/尾点、大小写/presentation-name、重叠规则、来源合并顺序、AdGuard 例外与失败保留旧代。
不能照搬 ESP 去掉 `www` 的规范化方式，或把多结果 mapper 改成任一哈希命中返回一个组。

mmap 为第二阶段候选：源指纹、索引版本和完整性校验，独立文件原子替换，旧代继续持有旧映射。
已触及映射页仍计 Linux RSS，也占系统页缓存；冷页有缺页延迟。小索引先常驻内存更简单。

## 4. 日志：先优化独有信息，再缩短重型详情保留

日志内存可拆为：`记录数 × 每条独有信息 + 共享内容 + 容器/索引 + 读取快照`。
普通查询环保存解析后的最终 Answer 和路由事实；逐步执行的 JSON 调试轨迹由手动抓取提供。
隐藏页面列或删 API JSON 字段并不会自动减少后端保留内容。

### 4.1 已有压缩与历史分布

[保留结构](../../../rust/native-host/src/observer/retention.rs) 已用精确长度域名、数值 Trace ID、共享模板和独立共享应答。
[5D-fix-B](../validation-records/10-10-5d-fix-b/README.md) 已把历史约 991.8 B/条降到 218.0 B/条，不能再按未压缩 AuditRecord 估算。

该历史 100,000 条环加最多 300 条独立慢查询，共 21,800,224 字节（20.79 MiB 请求堆）：

| 部分 | MiB | 占比 |
| --- | ---: | ---: |
| 逐条结构和 Arc 头 | 13.77 | 66.25% |
| 容器、重复时间表、共享提示表等 | 5.07 | 24.37% |
| 域名内容 | 1.81 | 8.71% |
| 共享模板、应答及其他 | 0.14 | 0.67% |

100,300 个保留对象只有 111 个共享模板、81 个共享应答，删少量共享字段收益很小。
该语料高度重复；TTL、轮转 IP、复杂 RR 和多路尝试会降低共享率，须对当前真实流量测量不同 payload 的数量与容量。

### 4.2 无损存储候选

1. **时间/耗时只存一份。** [observer.rs](../../../rust/native-host/src/observer.rs) 的 audit_timings 重复 row 的时间和耗时，每项 32 B；100k 条按当前容量增长到 131,072 项时约 4 MiB，400k 时约 16 MiB。可从记录/同页列数据生成窗口统计，维持一致快照、覆盖范围和边界语义。概览已只取覆盖范围，windows API 仍须兼容，读时扫描的 CPU/延迟需评估。
2. **Trace ID 共用前缀。** 页/生产者保存 nonce，逐条保存 counter，展示时恢复相同 ID；保持跨进程身份和非标准文本回退。
3. **按页保存紧凑记录。** 降低逐条 Arc 头、指针和分配器成本，快照共享不可变页。最多 300 条旧慢查询应独立保留小记录，避免一条旧慢查询钉住整页。clear/容量变更/读快照释放及两个 worker 的预算保持有界。
4. **客户端/域名用紧凑引用。** 随保留记录/页回收，不建立永久增长的全局域名表。名字几乎全唯一时，共享表可能反而增大，需能退化为连续字节池。完整 SocketAddr 无损表示还要处理端口、IPv6 scope/flow；日常 API 目前只显示 IP。
5. **应答正文与 TTL 分开共享。** 当前完整相等判断包含 TTL，内容相同但 TTL 不同的应答不能共享。将稳定 RR 内容与逐条真实 TTL 分开，不能从当前缓存补旧 TTL。
6. **减少读侧临时复制。** 通用筛选逐条克隆名字、IP、Trace ID、标签和 Answer；排行先逐条生成字符串再排序。借用或按内部 ID 聚合可降低查询时的分配/峰值，主要不影响闲置常驻量。

本地标准库布局模型：当前 row 字段组合 128 B，候选“时间/耗时/计数＋ID＋类型/状态”固定部分 56 B。
后者不含字典、应答、诊断、额外端口、页头、异常回退或快照，也未实现完整契约；只说明布局空间，不能当作每条总内存或生产 RSS。

### 4.3 信息保留建议与已确认方向

| 信息 | 方向 | 影响 |
| --- | --- | --- |
| 客户端、域名、完整最终 IP/CNAME、生效分流/来源、实际最终上游 | 较早普通成功查询继续可查（用户已确认够用） | 保持核心追查和完整地址/CNAME 搜索 |
| 时间、QTYPE、结果码、耗时、缓存/本地/失败状态 | 建议保留紧凑基本事实 | 定位查询，区分空答、拒绝、缓存和超时 |
| Trace ID | 保留关联功能，压缩表示 | 连接普通记录与主动抓取 |
| 完整分支、逐路尝试、最终序列、配置目标和中间标签 | 近期/异常/主动诊断详情候选 | 旧成功查询不必长期承载完整执行过程 |
| TTL 与特殊 RR 正文 | 详情可较短保留 | 旧普通成功查询无需完整回溯；具体窗口待设计 |
| QCLASS、AA/RA/TC | 不优先删除 | 字段小且已有共享，单独删除收益有限 |

`domain_set`、`effective_tag`、来源、配置上游组和实际 peer 表达不同事实；设计精简显示/存储时不能随意视为同一个值。
错误/慢查询详情也要有独立总预算，避免异常期间无界增长；超预算可保留基本事件并标明详情缺失。

日志条数也影响内存，但不能悄悄削减：按历史 218 B/条粗算，100k 约 21 MiB、20k 约 4 MiB，实际有容器与共享分布差别。
100k 条在 20/100/500 QPS 下仅约覆盖 83/17/3.3 分钟；容量不保证固定时长。
现有排行/窗口统计来自保留记录，不能偷换为全生命周期指标；如果需要长期统计，另定义统计范围。

手动诊断抓取最多 32,768 行、8 MiB 序列化内容，读取会清空，到期仅停止新增、已有内容继续可取。
可以另议未读内容过期释放；普通 log.file/stderr 为直接输出，调整 log.level 不会缩小查询审计环。

## 5. 其他内存线索与建议顺序

| 方向 | 代码事实 | 下一步 |
| --- | --- | --- |
| 构建输入共享 | build_mapper_matcher 仍逐条复制 rule/tag/source 到 ValuedRule，构建器内部借用已优化 | 按 provider 借用规则与共享结果描述，减少更新峰值 |
| 冷缓存过期清理 | 容量有界，过期冷键不主动回收 | 按完整 cache_expires_at 窗口分批清理，保持 lazy TTL 与导入时钟语义 |
| cache dump 共享快照 | key/response/domain_set 先深拷贝再编码，已有条数/字节限制 | 共享 Bytes/Arc，后台编码，保持捕获时事实、来源、格式与原子保存 |
| SRS/分页流式读取 | succinct 数据展开为 keys/String 再建索引；light_show 先完整加载再分页 | 减少中间对象，保持规范化、顺序、offset/search 与来源合并 |
| 上游 UDP 在途缓冲 | 每个等待中的 exchange 申请 65,535 B | 先量实际并发与贡献，再评估接收复用；不能缩小报文上限造成截断 |

缓存独立探针插入 100 条，逻辑过期后 live/snapshot 均为 0，底层仍保留 100；重查一个过期键后降至 99。
这是容量限制内的滞留，不是无界泄漏；回收堆也不保证 RSS 同步下降。
UDP 100/1000 个在途仅该缓冲约 6.25/62.5 MiB，是容量估算，未证实生产达到此并发。

建议分别测量、实施、验收域名索引与日志，避免混改后无法归因；构建输入共享可随索引一起评估。
分级日志以第 1 节用户决定为需求边界，先量固定表示和 payload 基数，再确定详情预算。

已有分配器调优（固定 mmap 阈值/trim/关闭本进程 THP）、审计共享、热应用启动代释放和一次性编译线程、route_learner 副本收敛不列为新成果。
见 [Mem-1](../validation-records/10-08-mem-1/README.md)、[审计压缩](../validation-records/10-10-5d-fix-b/README.md)、
[热应用回收](../validation-records/10-22-offthread-apply/README.md)、[route_learner](../validation-records/10-22-route-learner/README.md)。

## 6. 实施前的验证与研究证据

用当前完整配置在 Linux 单核建立基线：live heap、RSS/PSS、启动/规则 reload/连续设置和专属组热应用峰值；填满缓存与审计环，测随机域名、TTL 变化和复杂应答下的共享率。
同时验证正确查询的 p95/p99、CPU 和回收，不能只验索引字节。

- 域名：现有测试、规则与父/子/大小写/尾点变体、重叠来源、AdGuard 例外、最终路由审计、保存/重启、失败保留旧代及旧代释放。
- 日志：新旧表示的基本事实/完整详情、IP/CNAME 筛选、关联 ID、排行/覆盖统计、详情缺失状态、错误风暴预算、读中 clear/resize、热应用后历史来源以及快照释放。
- API/持久格式/默认设置的变更单独列明；研究结论不等于已完成迁移或冻结预算。

原始实验结果与独立实验工程已在 R4 精简；可用 `git show 359ba908:docs/rust/research/memory-optimization/<path>` 从保留的分支历史恢复。
当前结论和保留工具见[统一验证记录](../validation-records/10-25-memory-optimization/README.md#reproduction-provenance-and-cleanup)。
